# Luma Music 1.4 — roadmap

Luma Music 1.4 is a major product update built on the existing Rust core, native
Android UI, and Rust/egui desktop client. This document is a development plan,
not a claim that every listed feature is already implemented.

## Release principles

- Preserve `applicationId = org.luma.music`, the existing signing certificate,
  Android minSdk 30, and user data across upgrades.
- Keep business rules and shared models in `yamusic-core`; Kotlin owns Android
  UI and OS integration, while `luma-desktop` owns desktop presentation and OS
  integration.
- Do not duplicate catalog, queue, offline, or statistics rules in each client.
- Keep network/API behavior explicitly capability-gated and verify it against
  real accounts. Do not claim support based only on fixture tests.
- Keep the existing Luma visual identity: yellow accent, neutral surfaces,
  light/dark/OLED themes, restrained motion, and low-memory behavior.
- Deliver incrementally behind a dedicated feature branch and reviewable PRs.

## Baseline verified from the repository

The published 1.3 and current main/1.3.1 work already include:
- Rust workspace with `core` and `desktop`; Android calls Rust through JNI.
- Native Kotlin Views / Material 3 Android UI.
- Search for tracks, account/library access, playlists, likes/dislikes, queue,
  background playback, MediaSession, lyrics, and experimental My Wave.
- Basic offline MP3 storage and playback, cover cache, settings and OTA.
- Desktop search/playback with egui/eframe and rodio.
- Local history/bookmark/pin/backup persistence work in the Rust library store;
  Android integration and release status must be checked separately.

The 1.3.1 development notes still list catalog pages, playlist editing,
persistent download queue/resume, expanded Desktop screens, and several UI
integrations as unfinished. Those tasks must be audited before being repeated.

## Workstreams

### 0. Audit and release foundation
- Inventory current Android screens, JNI operations, Rust modules, SQLite schema,
  Desktop screens, workflows, and tests.
- Classify every 1.3.1 task as implemented, partial, missing, or broken.
- Record API request/response fixtures and real-account verification status.
- Preserve existing package ID, signing, ABI matrix, and upgrade path.

### 1. Shared Rust catalog
- Add typed search for tracks, albums, artists, and playlists.
- Add bounded pagination and stable response models.
- Add artist, album, and playlist detail operations only after validating the
  exact upstream API response shape.
- Keep cache entries bounded and scoped to the active account.
- Expose shared operations through the existing JNI/core dispatch contract.

### 2. Library and navigation
- Artist pages, discography, album pages, and track navigation.
- Library sections for likes, saved albums/artists where API supports them,
  recent items, and pinned items.
- Configurable home sections and recently opened items.
- Explicit empty, loading, stale, and error states.

### 3. Player and audio
- Preserve current playback while a new item is being prepared.
- Improve queue editing and persistence without losing the current slot/position.
- Verify gapless/crossfade feasibility against actual decoder and stream behavior
  before exposing controls.
- Improve audio-focus, route changes, Bluetooth, and recovery tests.
- Clearly distinguish system equalizer integration from an internal DSP.

### 4. Offline 2.0
- Durable download jobs with queued/running/paused/complete/failed/cancelled states.
- Retry, cancellation, progress, storage quota, and album/playlist grouping.
- Resume with HTTP Range only when the server confirms range support and byte
  identity; otherwise restart safely.
- Keep partial files private and publish only verified complete files atomically.
- Preserve account isolation and never persist OAuth tokens or signed stream URLs.

### 5. Android experience
- Modernize existing native Views / Material 3 screens without replacing the
  established Luma identity.
- Consistent spacing, typography, icons, list rows, loading/error/empty states.
- Responsive layouts, large font support, RTL, and reduced-effects mode.
- Avoid heavy blur, translucent layers, and continuous background animation.

### 6. Desktop 2.0
- Add catalog pages, library, playlists, and a full queue using shared core APIs.
- Improve OAuth UX and use OS credential storage where available.
- Add keyboard shortcuts, tray, mini-player, and output-device handling.
- Keep Windows 7/8/8.1 experimental until tested on real systems.

### 7. Personalization
- Complete history, bookmarks, local listening statistics, and home layout.
- Add monthly/yearly recap cards only from locally available, reliable data.
- Keep statistics local by default and make data export/clear explicit.

### 8. Playlists and My Wave
- Create, rename, edit, reorder, and delete playlists only with server-confirmed
  results and stale-response protection.
- Expand My Wave settings/history/feedback only for verified API capabilities.
- Do not optimistically show success when the server response is ambiguous.

### 9. Stabilization and release
- Rust, Python, JVM, lint, ABI, packaging, and Desktop workflow checks.
- Migration and upgrade tests from 1.3 / 1.3.1 data.
- Real-device tests on Android API 30+ and low-memory hardware.
- Real-account network tests separated from offline fixture tests.
- Verify APK signatures, SHA-256, 16 KiB alignment, and all supported packages.

## Suggested delivery order

1. Audit and architecture contract.
2. Shared Rust catalog API.
3. Android catalog and library.
4. Player and queue improvements.
5. Offline manager.
6. Android visual refresh.
7. Desktop catalog and library.
8. Statistics and playlist/My Wave completion.
9. RC hardening and release.

The workstreams can overlap after the shared API contracts are stable. Do not
start a large UI rewrite before the core response models and error semantics are
settled.

## Definition of done

A feature is complete only when its core logic has tests, client integration is
implemented, loading/error/empty states are handled, account boundaries are
respected, and the relevant platform workflow passes. Network-dependent features
also require a documented real-account test; compilation alone is insufficient.
