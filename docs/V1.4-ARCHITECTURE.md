# Luma Music 1.4 — architecture notes

## Existing architecture to preserve

- Cargo workspace: `core` and `desktop`.
- Rust crate `yamusic-core` is built as cdylib/rlib/staticlib.
- Android calls Rust through the existing JNI methods in `core/src/lib.rs`.
- Android UI is native Kotlin Views / Material 3; Android services and OS APIs
  remain in Kotlin.
- Desktop is a Rust egui/eframe client using the same `yamusic-core` dispatch
  API and its own rodio audio output.
- SQLite persistence is owned by Rust. Android Keystore remains responsible for
  account secrets; secrets must not be copied into the database or backups.

## 1.4 module ownership

| Concern | Owner | Notes |
| --- | --- | --- |
| API client and response parsing | `core` | Bounded response size, trusted hosts, timeouts |
| Catalog/search models | `core` | Shared by Android and Desktop |
| Library, pins, history, bookmarks | `core` | SQLite, bounded and account-scoped |
| Playlist mutation rules | `core` | Server confirmation required |
| Playback queue rules | `core` | Preserve slot identity and position |
| Offline metadata and integrity | `core` | Atomic files, quota, account isolation |
| Android screens and navigation | Kotlin | Native Views / Material 3 |
| Android playback service | Kotlin + core | MediaSession, Audio Focus, notifications |
| Desktop UI and OS integration | `desktop` | egui/eframe, tray and shortcuts |
| Desktop audio output | `desktop` | Keep platform-specific output here |

## Core/client contract

New operations should use the existing JSON dispatch envelope:
`{"ok":true,"data":...}` or `{"ok":false,"error":"..."}`.

For each operation:
- Validate input size, enum values, IDs, and pagination in Rust.
- Return stable, documented JSON fields.
- Do not expose raw OAuth tokens or signed audio URLs in persisted state.
- Make cancellation and stale-response behavior explicit for asynchronous clients.
- Keep server errors distinguishable from malformed local input where possible.

The first 1.4 catalog operation, `catalog_search`, accepts:
`{"query":"...","kind":"track|album|artist|playlist","page":0}`.
Rust validates the query, kind, and page; track records are converted into the
shared Track shape, while album/artist/playlist records retain their type-specific
metadata and receive only validated public artwork URLs. Android uses this
operation for category-based catalog search and pagination. Track results feed
the existing player queue, playlist results use the existing playlist loader,
and album/artist results currently expose summary metadata only. Desktop catalog
screens and full album/artist detail operations are not yet implemented.

## SQLite policy

- Add schema changes with monotonic `user_version` migrations.
- Migrations must be transactional and safe to run more than once.
- Never delete or recreate the user's existing settings, playback state, history,
  bookmarks, pins, or offline files to perform an upgrade.
- Keep OAuth credentials outside SQLite.
- Bound rows and serialized payload sizes.
- Add migration tests using a database fixture from the previous schema.

## Compatibility invariants

- Android application ID remains `org.luma.music`.
- Preserve the user's existing signing certificate.
- Keep minSdk 30 unless a separately reviewed compatibility decision is made.
- Do not raise versionCode/versionName to a release value until the release branch
  and upgrade tests are ready.
- Keep all currently supported Android ABIs and verify 16 KiB packaging.
- Desktop target limitations must be documented per platform.

## UI principles

- Retain the existing Luma visual identity and yellow accent.
- Prefer native, opaque Material surfaces and restrained transitions.
- Honor reduced-effects and low-memory behavior.
- Provide loading, empty, error, and retry states for every network-backed screen.
- Avoid duplicating server-side business rules in Kotlin or egui.


## Catalog detail operations

- `catalog_album` validates a numeric album ID and reads
  `/albums/{id}/with-tracks`. Rust normalizes all tracks in every volume so
  multi-disc albums preserve disc order and can be played by both clients.
- `catalog_artist` validates a numeric artist ID and reads
  `/artists/{id}/brief-info`. Artist, release, and popular-track metadata is
  normalized for the Android and Desktop clients.
- Android exposes album track lists and artist release/popular-track sections.
  Desktop exposes the same navigation and routes selected tracks into its
  existing playback queue.
- The Desktop CI workflow checks formatting, core tests, Desktop tests, and
  release builds on Linux, Windows, and macOS for relevant pull requests.


## Playlist mutation contract

Android playlist edits use Rust-owned operations: `playlist_create`,
`playlist_rename`, `playlist_delete`, `playlist_detail`,
`playlist_insert_track`, and `playlist_delete_track`.

- Mutations validate numeric owner/playlist/track/album identifiers in Rust.
- Rename, delete, and track changes verify that the requested owner matches the
  authenticated account; other users' playlists remain read-only.
- Insert/remove operations send a server revision and a structured
  `change-relative` diff. The client refreshes playlist details before adding
  tracks and after successful mutations rather than optimistically changing UI.
- Android exposes create, rename, delete, add-to-playlist, and remove-from-
  playlist actions. Desktop playlist editing remains unfinished.


## Desktop playlist integration

Desktop can load the authenticated user's playlist library, create private
playlists, rename existing playlists, open playlist details, and add a selected
catalog track. Before insertion it fetches the latest playlist revision and
track count, then uses the same Rust-owned mutation operation as Android.
Desktop playlist deletion and per-track reorder/removal controls remain pending.
